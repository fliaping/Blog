用 AI 写出一个函数，和用 AI 交付一条可靠的生产链路，是两件难度很不一样的事。

前者很容易给人惊喜：解释需求、生成代码、补齐测试，往往很快就有结果。后者却会不断遇到新的问题：代码能运行，数据未必完整；脚本说成功，下游未必收到；报告写得漂亮，指标口径也可能是错的。

在持续使用 AI 参与研发之后，我越来越关注的不是它写了多少行代码，而是它能否帮助我把需求更快地推进到**可执行、可验证、可交付**的状态。

这需要的不只是一个更好的 Prompt，还需要一套让 AI 能稳定工作的工程环境。本文把这套环境称为 **Harness**：它像挽具一样，把模型的能力接到真实任务、工具和反馈上。

![AI Coding：连接目标、上下文、执行与证据的交付闭环](https://fliaping-blog.oss-rg-china-mainland.aliyuncs.com/storage/2026-10-09/21-11/ai-coding-harness/01-cover.png)

*本文由一次研发实践分享整理而来。案例已抽象为通用场景，配图为重新绘制的方法示意，不包含具体组织、内部系统和业务指标。*

## 1. 提效发生在整条链路上

很多人判断 AI Coding 有没有用，会先看编码速度。但真实项目里，写代码只是交付过程的一部分。

需求需要澄清，历史决策需要理解，运行环境需要准备，数据需要核对，失败需要归因。还要补脚本、看日志、整理报告，让下一位接手的人知道发生了什么。

这些工作单独看都不显眼，却决定一个项目能不能完成。AI 的价值常常就发生在这里：把原本停留在讨论里的方案变成可运行的脚本，把一句“查一下问题”变成有步骤的排查，把分散的执行结果整理成能追踪的证据。

它也降低了进入陌生模块的成本。一个主要写后端的工程师，可以借助 AI 更快理解数据处理、评测和运行工具；一个熟悉算法的工程师，也可以更快补齐接口、任务编排和观测能力。

但进入一个领域更容易，不等于已经拥有这个领域的判断力。**AI 放大的是执行能力，工程师仍要判断目标是否正确、约束是否被破坏、证据是否足够。**

因此，我更愿意用端到端的交付周期、返工情况、失败恢复能力和经验复用程度来观察提效，而不是只统计代码量。

## 2. 从 Prompt 到 Context，再到 Harness

这三个概念可以理解为逐步补齐的三个层次。它们相互配合，并不是后一个出现后，前一个就不再需要。

![Prompt、Context、Harness：分别解决意图表达、项目理解和稳定交付](https://fliaping-blog.oss-rg-china-mainland.aliyuncs.com/storage/2026-10-09/21-11/ai-coding-harness/02-three-layers.png)

### Prompt：把意图表达清楚

Prompt 关注的是怎么问：任务是什么、输出什么、有哪些限制，必要时给出示例。

小任务里，一段清楚的指令可能就够了。但真实工程涉及多份材料、多轮修改和多次验证，单次问答无法承载全部状态。

### Context：让 AI 从正确的地方理解项目

Context 关注的是给模型看什么、什么时候看、看多少。代码、文档、日志、样本和历史决策，都属于上下文。

问题通常不是资料不够多，而是缺少入口。把整个仓库和所有历史记录一次性塞进去，重要约束反而容易被淹没。

更好的办法是先给一张地图：系统解决什么问题，核心链路在哪里，常见任务从哪个入口开始，哪些决策有明确原因。需要细节时，再按需打开材料。

### Harness：让执行进入反馈闭环

有了上下文，AI 也未必会主动验证，更未必知道什么时候应该停下来。

所以还需要把执行方式、验证条件和反馈路径放到模型之外：标准命令、自动检查、可追踪状态、权限边界，以及失败后要更新的文档和工具。

在本文的语境里：

> Harness 是让 AI 在有上下文入口、有阶段约束、有验证门禁、有经验回写的工程现场里工作。

当交付对象涉及服务或数据时，运行稳定性也必须成为这个现场的一部分。代码正确只是起点，结果还需要完整、可恢复、能被下游使用。

## 3. 为什么“看起来完成”最危险

我遇到的问题，大致可以归到四类。

| 表现 | 隐藏的问题 | 更可靠的约束 |
| --- | --- | --- |
| 一轮改很多地方 | 改动面扩大，隐含约束被遗漏 | 划定边界，逐阶段推进 |
| 很快宣布完成 | 代码改完，但没有运行或核对 | 定义验收证据，实际执行检查 |
| 语法正确、逻辑顺畅 | 实现偏离了任务需要的语义 | 明确不变量，设计边界用例 |
| 顺手清理或重置 | 操作影响超出当前任务 | 限定权限，预演高风险动作 |

“已修复”“已上传”“测试通过”都是结论。交付需要的是结论背后的证据：执行了什么命令，结果在哪里，核对了哪些条件，还剩哪些问题。

尤其是跨阶段任务，局部成功不等于整体成功。一个阶段生成了文件，另一个阶段更新了状态，最后一个阶段仍可能没有把结果写到目标位置。

### 一个通用例子：分片稳定性

假设有一批对象要交给多个 worker 处理，任务可能中断后重跑。下面的分配方式很直观：

```python
worker_id = index % worker_count
```

但如果重跑时输入顺序变化，同一个对象就可能换到另一片。对于依赖分片状态恢复进度的系统，这会让续跑和对账变得困难。

此时需要明确的约束是：**在 worker 数量和哈希规则不变时，同一个对象必须落到同一片。**

```python
# stable_hash 必须在不同进程、不同运行之间保持一致
worker_id = stable_hash(object_id) % worker_count
```

这里不能直接假定语言内置的 hash 满足要求。worker 数量改变时，也要重新考虑分片与状态迁移。

这个例子不是说轮转分配总是错误，而是说明：**代码是否正确，取决于任务要求它保持什么。** 把这个不变量写下来，并用“打乱输入后重跑”的用例检查，比一句“注意稳定性”更有效。

## 4. 把 Harness 落到五个具体位置

![交付 Harness 的五个位置：上下文、阶段校验、质量、稳定性、经验沉淀](https://fliaping-blog.oss-rg-china-mainland.aliyuncs.com/storage/2026-10-09/21-11/ai-coding-harness/03-delivery-harness.png)

### 上下文：静态事实与动态证据一起给

稳定的信息适合放在仓库里：需求边界、数据口径、方案决策、运行说明、常见问题。

会变化的信息则要通过工具获取：当前任务状态、最新日志、实际数据结构、输出样本和依赖服务的响应。

只有文档，容易拿旧事实做判断；只有工具，又容易反复探索同一个系统。两者配合，AI 才能既知道“为什么”，又看到“现在是什么样”。

工具也需要边界：返回必要字段、限制查询范围、保留可追踪的执行记录。生产数据不应该因为“补充上下文”就被复制到不合适的地方。

### 阶段：每一步都定义完成条件

把任务拆成“处理、评测、写入、对账”，只是第一步。还要说明每一步产出什么，后续阶段如何验证它。

例如，“写入完成”的验收条件应落在目标系统上：目标位置存在，时间范围正确，记录可查询，关键字段可核对。只看上传进程退出码，还不足以证明下游已经拿到正确结果。

一个尤其值得防范的设计，是把“停止重试”直接标成“成功完成”。超过重试上限只说明不再继续尝试，不能证明已有合格结果。

### 质量：先审口径，再看数字

假设要判断一条记录是否有有效信息。如果评估脚本只检查一个经常为空的字段，就可能把其他字段有值的记录全部判成无效。报告格式再工整，也改变不了口径错误。

检查不能只问“有没有问题”，而要提出可验证的假设：

- 有没有关键字段缺失？空值和合法的零值是否区分？
- 异常是否集中在某一类输入？
- 抽样方式有没有遗漏失败记录？
- 边界样本是否被误判？
- 报告中的指标，是否与原始样本和业务定义一致？

**验收脚本本身也是待验证的代码。** AI 可以帮助执行检查，但检查什么、怎样发现问题，仍需要工程判断。

### 稳定性：小样本跑通之后，还有另一组问题

进入批处理或线上服务后，需要面对超时、限流、重试、资源占用、降级和恢复。

我不再把“优化性能”作为一个笼统指令交给 AI。更有用的是先分解问题：时间花在请求等待、计算、序列化还是写入？队列在哪里堆积？并发增加之后，内存和错误率怎么变化？

方向明确后，再让 AI 实现方案、运行有边界的实验、比较结果。否则很容易改了并发参数，却碰不到真正的瓶颈。

限速反馈也要符合任务语义。用全程累计错误率做控制，可能让早期故障长时间影响后续决策；使用近期窗口时，又要处理样本不足和反馈抖动。先定义控制目标，再选择算法。

### 沉淀：每次失败都更新下一次的工作环境

修完一个问题后，还应该问：为什么它会发生？

缺少上下文，就补入口；状态语义模糊，就补状态定义和测试；运行方式不统一，就补脚本；验收漏了一个角度，就补检查清单。

重复且稳定的操作，可以封装成 Skill：写清适用场景、输入输出、执行入口和验证条件。不能把聊天记录原样堆进去，就认为已经沉淀了能力。

## 5. 用跨阶段对账，识别“伪完成”

在一条抽象的批处理链路里，通常至少存在三份事实：输入清单、执行状态和最终结果。它们各自看起来正常，放在一起却可能对不上。

![跨阶段对账：输入、状态与结果互相核对，缺失记录进入恢复流程](https://fliaping-blog.oss-rg-china-mainland.aliyuncs.com/storage/2026-10-09/21-11/ai-coding-harness/04-reconciliation.png)

一个可用的起点是明确三个集合：

- **E：应处理集合**。本轮任务实际应覆盖的对象。
- **V：有效结果集合**。通过质量检查、已写入目标位置的对象。
- **D：明确处置集合**。按约定排除或延期、带有原因记录的对象。

缺失集合是：

```text
missing = E − (V ∪ D)
```

还要检查重复、范围外结果，以及执行状态与结果之间的冲突。只有任务允许排除或延期时，D 才能算作有明确去向；如果本轮要求全部产出，D 仍属于未完成项。

这套集合表达只是教学示意。真实任务还要约定核对粒度、主键、结果版本和时间边界，不能把不同批次的结果混在一起。

对账的价值，是把“AI 说完成了”变成“每个应处理对象都有可核对的去向”。

这一思路也适用于普通应用：接口返回成功，要核对持久化结果；迁移脚本执行完成，要检查目标数据；部署命令结束，要检查服务是否真的可用。

## 6. 团队事实源，要能被执行和验证

需求在聊天里、方案在在线文档里、命令在个人终端历史里、结论在截图里。人还能靠记忆把这些东西串起来，AI 接手时却经常要从零探索。

我倾向于把与交付有关的稳定信息沉到仓库里，也就是 **Repo as Truth**。仓库不仅保存代码，也保存决策、运行入口和证据索引。

这并不是要求把所有原始数据和日志都提交进 Git。大文件、敏感数据和运行产物可以留在受控存储中；仓库保留它们的用途、获取方式、版本及验证说明。

一个最小的组织方式可以是：

```text
README            系统地图与常用入口
docs/             需求、方案、口径与决策
scripts/          可重复执行的工具
tests/            关键不变量与边界用例
skills/           可复用的任务流程
reports/          脱敏后的结论或证据索引
```

执行环境也要相对稳定。共享开发环境、容器或独立工作区都可以，关键是依赖、运行命令、样本版本和结果路径能被追踪。多人或多个 Agent 并行时，应隔离写入范围，避免相互覆盖状态。

任务最后留下的，不应该只有一段聊天总结，而应该包括：改动、验证命令、结果位置、未解决问题，以及必要的文档更新。

![经验复用循环：发现问题、定位原因、固化约束、验证后在下一任务复用](https://fliaping-blog.oss-rg-china-mainland.aliyuncs.com/storage/2026-10-09/21-11/ai-coding-harness/05-reuse-loop.png)

第一个任务里，我们花时间补工具链、理解失败模式、统一口径。后续任务可以从这些资产出发，减少重复探索。

这种复用并不会自动发生。文档过期、工具不可运行、Skill 不说明适用边界，都可能让旧经验成为新的负担。沉淀之后，还要持续维护。

## 7. 明天就能开始的三个动作

不必先搭一套庞大的平台。可以从一个真实任务开始。

**第一，写一份上下文入口。** 用一页说明系统目标、核心链路、常见命令和不能破坏的约束。让 AI 从这里开始，按需深入。

**第二，动手前对齐目标与验证方式。** 让 AI 先复述边界，列出不确定问题，说明怎样证明任务完成。步骤的多少取决于复杂度，不必给小改动套上重流程。

**第三，把完成声明换成证据。** 要求给出运行结果、目标位置、核对过程和遗留问题。失败时，同步更新相应约束或工具。

一个简短的任务模板就能把这些要求连起来：

```text
目标：这次交付要改变什么？
边界：哪些约束必须保持，哪些操作不在范围内？
入口：先读哪些材料，使用哪些工具获取当前事实？
计划：如何拆阶段，在哪些节点验证？
验收：用什么命令、样本和结果证明完成？
回写：发现新问题后，更新哪份文档、脚本或检查项？
```

需要并行时，优先拆真正独立的任务，并为每个任务划定写入范围。需要 Agent 长时间自主执行时，先把验收条件和停止条件定义清楚。自主运行时间更长，只有在结果可检查的前提下才有价值。

## 8. 工程师的价值，更集中在判断上

AI 可以承担更多阅读、实现、运行和整理工作。工程师则需要更认真地定义问题、理解约束、设计检查，并在证据不足时提出质疑。

这不是轻松地把工作丢出去。它要求我们更清楚地知道：什么值得自动化，什么应该保留判断；什么算局部成功，什么才算真实交付。

AI 写代码不难。难的是让它理解：**为什么这里不能这么写，又应该用什么证据证明另一种写法是对的。**

Harness 的作用，就是把这些判断变成可执行的入口、可检查的约束和可复用的经验，让一次任务中的收获真正进入下一次交付。
